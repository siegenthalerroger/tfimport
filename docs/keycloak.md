# Keycloak provider support

This document describes the state of `tfimport`'s support for the
[Keycloak Terraform provider](https://registry.terraform.io/providers/keycloak/keycloak/latest)
(`keycloak_*` resources).

## How Keycloak import IDs work

Almost every Keycloak resource is imported with a composite ID of the form
`{{realm}}/{{guid}}` (sometimes deeper, e.g. `{{realm}}/client/{{clientGuid}}/{{mapperGuid}}`).
The `guid` parts are **server-generated** UUIDs that Keycloak assigns on
creation, so they are not present in a Terraform plan. `tfimport` therefore
resolves them in two layers:

1. **Static mappings** (`internal/providers/keycloak.go`, generated by the Doc
   Cruncher). These handle resources whose ID is fully derivable from
   configuration — no GUID involved.
2. **Custom resolvers** (`internal/providers/keycloak_resolvers.go`). These query
   the Keycloak admin REST API to look the GUID up by the resource's natural key
   (clientId, username, name, alias, …). The custom resolver runs first; when it
   returns nothing the static mapping applies.

### The single-match rule

To avoid emitting a wrong import ID, a resolver returns a value **only when
exactly one** object matches the natural key. The richer
`ResolveKeycloakImportID` distinguishes the outcomes:

| Status                | Meaning                                                        |
|-----------------------|----------------------------------------------------------------|
| `KeycloakResolved`    | exactly one match; `ImportID` is set                           |
| `KeycloakNotFound`    | zero matches — usually a genuinely new resource to be created  |
| `KeycloakAmbiguous`   | multiple matches; `Candidates` lists them                      |
| `KeycloakSkipped`     | missing prerequisite (no realm/credentials/parent/natural key) |
| `KeycloakError`       | the API lookup failed                                          |

The string hook consumed by core `tfimport` today returns an ID only for
`KeycloakResolved` and `""` for everything else. The `Candidates` on an ambiguous
result are not yet surfaced to the user — that is intended for a follow-up change
to core `tfimport` (see [Not yet supported](#not-yet-supported)).

## Configuration

The admin client is built lazily from the same environment variables as the
Keycloak provider. If `KEYCLOAK_URL` or credentials are absent, API resolution is
skipped (an informational line is logged) and only the static mappings apply.

| Variable | Purpose |
|----------|---------|
| `KEYCLOAK_URL` | base URL of the Keycloak instance (required for API resolution) |
| `KEYCLOAK_CLIENT_ID` | client used to authenticate (defaults to `admin-cli` for password grant) |
| `KEYCLOAK_CLIENT_SECRET` | enables the `client_credentials` grant |
| `KEYCLOAK_USER` / `KEYCLOAK_PASSWORD` | enables the `password` grant |
| `KEYCLOAK_ACCESS_TOKEN` | use a pre-obtained bearer token instead of authenticating |
| `KEYCLOAK_REALM` | realm used to authenticate (default `master`) |
| `KEYCLOAK_ADMIN_URL` | admin URL if different from `KEYCLOAK_URL` |
| `KEYCLOAK_BASE_PATH` | base path (e.g. `/auth` on older Keycloak) |
| `KEYCLOAK_CLIENT_TIMEOUT` | HTTP timeout in seconds (default `15`) |

## Supported resources

### Statically derived (no API call)

| Resource | Import ID |
|----------|-----------|
| `keycloak_realm` | realm name |
| `keycloak_oidc_identity_provider`, `keycloak_saml_identity_provider`, `keycloak_kubernetes_identity_provider`, `keycloak_spiffe_identity_provider` | `realm/alias` |
| `keycloak_default_groups` | `realm` |
| `keycloak_required_action` | `realm/alias` |

### Resolved via the admin API (natural key → GUID)

Top-level resources, matched by the listed key within the realm:

| Resource | Matched by |
|----------|------------|
| `keycloak_openid_client`, `keycloak_saml_client` | `client_id` (the clientId) |
| `keycloak_user` | `username` |
| `keycloak_openid_client_scope`, `keycloak_saml_client_scope` | `name` |
| `keycloak_role` (realm role) | `name` |
| `keycloak_role` (client role) | `name` within the client GUID in `client_id` |
| `keycloak_group` (top-level) | `name` |
| `keycloak_authentication_flow` | `alias` |
| `keycloak_ldap_user_federation`, `keycloak_custom_user_federation` | `name` |

### Nested resources (parent GUID + natural key)

These resolve the parent's GUID first, then match the child by name. The parent
GUID is taken from concrete config when the **parent already exists in state**,
or resolved by tracing the Terraform reference when the **parent is being
imported in the same plan** (the Expression Tracer pattern; see
`resolveAttribute` in `aws_resolvers.go`, reused via `tracedGUID`). Identity
provider mappers are keyed by the plain `identity_provider_alias`, so they need
no tracing.

| Resource family | Parent (reference attribute) | Import ID |
|-----------------|------------------------------|-----------|
| nested `keycloak_group` | parent group (`parent_id`) | `realm/childGuid` |
| `keycloak_ldap_*_mapper`, `keycloak_hardcoded_attribute_mapper` | user federation (`ldap_user_federation_id`) | `realm/fedGuid/mapperGuid` |
| `keycloak_*_protocol_mapper`, `keycloak_generic_protocol_mapper`, `keycloak_generic_client_protocol_mapper` | client (`client_id`) or client scope (`client_scope_id`) | `realm/client/{guid}/{mapperGuid}` or `realm/client-scope/{guid}/{mapperGuid}` |
| `keycloak_*_identity_provider_mapper` | identity provider (`identity_provider_alias`) | `realm/alias/mapperGuid` |
| `keycloak_openid_client_authorization_{resource,scope,permission}` and `keycloak_openid_client_*_policy` | resource-server client (`resource_server_id`) | `realm/resourceServerGuid/objectGuid` |

## Not yet supported

The following are intentionally left returning `""` (reported as "cannot be
imported"); contributions welcome.

- **Multi-hop / multi-parent chains.** Resources whose ID depends on resolving
  *two or more* server-generated GUIDs in sequence are not yet handled, because
  `tracedGUID` resolves a single parent level. The Expression Tracer reuses the
  current resource's context when recursing, so a parent that itself needs
  tracing (a grandparent) is not resolved. Affected resources include:
  - `keycloak_authentication_execution`, `keycloak_authentication_execution_config`,
    `keycloak_authentication_subflow` (flow → execution → config chain).
  - `keycloak_openid_client_service_account_role`,
    `keycloak_openid_client_service_account_realm_role`
    (realm → service-account user → client → role).
  - `keycloak_generic_role_mapper`, `keycloak_generic_client_role_mapper`
    (role-assignment associations across two resolved objects).
  - Deeply nested groups (sub-group of a sub-group), where the parent chain
    exceeds one traced level.
- **Feasible but not yet wired up:** `keycloak_group_roles`,
  `keycloak_identity_provider_token_exchange_scope_permission`,
  `keycloak_default_roles`.
- **Not importable by design** (the provider itself does not support import, or
  the resource is a realm-level singleton without a stable GUID):
  `keycloak_group_memberships`, `keycloak_*_permissions`,
  `keycloak_realm_*_client_scopes`, `keycloak_realm_events`,
  `keycloak_realm_localization`, `keycloak_realm_user_profile`,
  `keycloak_realm_keystore_*`, `keycloak_user_groups`, and similar.

### Surfacing ambiguous matches (planned, separate PR)

When several objects match a natural key, the resolver already collects them in
`KeycloakResolution.Candidates`, but core `tfimport` only consumes the resolved
string today. A follow-up change to core can read the full `KeycloakResolution`
and print the candidate GUIDs so the user can pick one. This package does not
need further changes for that.

## Running the integration tests

The unit tests use a fake client and run by default. The integration tests
(`keycloak_integration_test.go`, build tag `integration`) exercise the resolvers
and the HTTP client against a real Keycloak:

```bash
docker run -d -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  keycloak/keycloak:26.6.1 start-dev

KEYCLOAK_URL=http://localhost:8080 \
KEYCLOAK_USER=admin KEYCLOAK_PASSWORD=admin \
  go test -tags integration ./internal/providers/ -run Integration -v
```

The test creates a throwaway realm, seeds resources, asserts the resolved import
IDs (including a nested protocol mapper and a nested group), and deletes the
realm afterward.

## Regenerating the static mappings

When the provider adds or changes resources, regenerate `keycloak.go` from the
provider's documentation (see `AGENTS.md` for the Doc Cruncher workflow):

```bash
cd scripts
go run . -provider=keycloak -docs=/path/to/terraform-provider-keycloak/docs/resources
```

The custom resolvers and the admin client live in separate files
(`keycloak_resolvers.go`, `keycloak_client.go`) and are never overwritten by the
generator.
